# 통신 관측 및 지속 최적화 작업 계획

작성일: 2026-09-10 KST
상태: 계획 작성 완료 / 구현 및 운영 반영 전

## 1. 목표와 핵심 전략

프록시의 오류 원인, 응답 지연, 스트림 중단을 측정할 수 있게 만들고, 동일 조건의 변경 전후 비교로 최적화 효과를 검증한다. 먼저 관측 정확성과 안전성을 확보하고 실제 병목이 확인된 뒤 동작을 최적화한다.

완료 시 사용자는 최근 3시간 보고서에서 다음 질문에 답할 수 있어야 한다.

- 어느 경로에서 오류가 발생했으며, upstream 응답인지 로컬 연결·인증 실패인지?
- 첫 응답과 첫 본문이 오기까지 얼마나 걸렸으며, 평소보다 느려졌는지?
- HTTP 200 이후 전송이 끝났는지, 사용자가 취소했는지, upstream이 끊겼는지?
- 계정 전환·HTTP 전환이 정상 정책에 따른 것인지?
- 측정 자료가 누락되었는지, 개선 전후 비교에 충분한 표본이 있는지?

## 2. 확인된 현황

- `internal/gateway/gateway.go`: RequestEvent는 메서드·프로필·상태·전환 정보만 보유한다. ModifyResponse에서 상태를 기록하므로 본문 전송 완료를 증명하지 못한다.
- ErrorHandler는 원래 오류를 분류하지 않고 502로 기록한다. 인증 취득 실패도 502지만 별도 오류 분류가 없다.
- `internal/app/app.go`: 간략 텍스트를 stdout으로 출력한다. `/healthz`는 로컬 생존 확인이며 upstream 통신 상태를 보장하지 않는다.
- Responses WebSocket의 HTTP 426 전환은 의도된 정책이다. 일반 WebSocket 전달은 유지해야 한다.
- 직전 운영 점검(20:52:35~23:52:35 KST): 프록시 응답 364건, 502 1건, 404 8건, 405 4건, HTTP 전환 11건. 이 수치는 헤더 상태 집계이며 스트림 성공률이 아니다.
- 실행 컨테이너는 `localsubproxy`, 이미지 `ai-auth-proxy:local`, 데이터는 `%APPDATA%/LocalSubProxy`. 현재 Compose는 `gpt-codex-router`와 다른 데이터 루트를 사용한다. 현재 소스와 실행 바이너리의 일치는 미확인이다.
- Docker 로그 드라이버는 json-file이며 컨테이너별 회전 옵션은 비어 있었다. 데몬 기본값은 별도 확인이 필요하다.
- 작성 당시 `setup.sh`에 기존 미커밋 변경이 있다. 구현 시 보존한다.

## 3. 범위와 경계

이번 구현 범위는 구조화 로그, 요청 생명주기 측정, 보관 정책, 로컬 분석 명령, 검증 및 운영 적용 절차다. 초기에는 별도 외부 관측 서비스나 대시보드 서버 없이 동작하도록 한다.

인증·계정 전환 정책, upstream 재시도 정책, 호스트 loopback 바인딩을 관측 기능 때문에 바꾸지 않는다. HTTP 오류를 줄이기 위한 임의 재시도는 하지 않는다. 실제 최적화는 관측 결과를 바탕으로 후속 변경으로 수행한다.

원본 프롬프트·응답 본문·OAuth 토큰·쿠키·ChatGPT 계정 ID·쿼리 문자열·전체 헤더를 저장하지 않는다. 오류 객체 문자열과 upstream 오류 본문도 그대로 출력하지 않는다. 운영 로그와 보고서는 저장소·패키지에 포함하지 않는다.

## 4. 단계별 작업

### P0 — 실행 환경과 측정 계약 확정

1. 실제 컨테이너 이미지 ID, 실행 명령, mount, Compose 소유 경로, 로그 옵션을 확인한다. 환경 변수 전체나 인증 파일을 출력하지 않는다.
2. 현재 소스와 바이너리 버전의 관계를 확인한다. 빌드 버전·커밋·관측 스키마 버전을 시작 이벤트에 기록하도록 계획한다. 확인 불가한 버전은 unknown으로 둔다.
3. 기존 데이터 루트를 유지할 배포 명세를 확정한다. 새 기본 경로로 빈 프로필을 만들거나 두 프록시를 같은 프로필에 연결하지 않는다.
4. 아래 이벤트·타이밍·완료 상태 계약을 먼저 문서화한다.

완료 기준: 기존 인증 데이터와 서비스 매핑이 명확하고, 누가 구현해도 같은 의미로 집계할 수 있는 필드 계약이 있다.

### P1 — 안전한 구조화 로그와 요청 추적

주요 대상: `internal/gateway/gateway.go`, `internal/app/app.go`, 필요 시 `internal/observability/` 신규 패키지.

- JSON Lines, UTC 타임스탬프, schema_version, 서비스 버전을 사용한다. 보고서 표시는 KST를 지원한다.
- 게이트웨이가 생성한 request_id로 시작·upstream 시도·계정 전환·최종 종료 이벤트를 연결한다. 클라이언트 제공 ID를 신뢰하거나 그대로 기록하지 않는다.
- 요청 하나에 시작 1건과 최종 종료 1건을 기록한다. 계정 전환에 따른 시도는 attempt 번호로 분리하고 요청 수와 재시도 수를 혼동하지 않는다.
- 필드: method, route_template, transport, 비식별 profile_ref, status_code, status_origin, outcome, error_category, attempt, 소요 시간, 전달 바이트 수.
- 경로는 알려진 정적 경로 및 동적 구간을 제거한 템플릿으로 기록한다. 알 수 없는 경로는 unknown으로 묶고 임의 문자열을 보관하지 않는다. 필요한 경로 분류는 명시적으로 추가한다.
- 요청 출처는 peer_class(loopback/container-network/other/unknown) 정도로 제한한다. 전달 헤더는 신뢰하지 않는다. Docker NAT 때문에 실제 호출 앱·사용자를 식별할 수 없다는 한계를 보고한다.
- 오류는 auth_unavailable, dns, connect, tls, upstream_timeout, upstream_http, upstream_read, downstream_write, client_cancel, unknown 등 제한된 값으로 분류한다. 증거가 불충분하면 unknown을 유지한다.
- 정상 HTTP 전환은 transport_fallback로 기록하고 장애율에서 분리한다. 로컬 거절 응답 및 인증 실패도 누락 없이 기록한다.

완료 기준: 합성 404/405/502의 경로 분류와 발생 계층을 구분하며, 민감 정보가 어떤 이벤트에도 남지 않는다.

### P2 — 지연 및 스트림 종료 측정

- gateway_total_ms: 진입부터 핸들러 종료까지. 사용자 입력부터의 전체 지연과 구분한다.
- auth_ms: 자격 증명 취득에 걸린 시간. 필요 시 refresh 발생 여부를 제한된 상태 이벤트로 연결한다.
- upstream_headers_ms: 각 시도 시작부터 upstream 헤더 수신까지.
- first_body_ms: 요청 진입부터 첫 본문 바이트를 downstream에 쓰기까지. 본문이 없으면 null이며, 모델의 첫 토큰 시간으로 표현하지 않는다.
- response_bytes: 실제 downstream에 쓴 본문 바이트. Content-Length로 대체하지 않는다.
- outcome은 body_eof, client_cancel, upstream_read_error, downstream_write_error, upgrade_closed, unknown 등으로 나눈다. HTTP 상태와 전송 결과를 별도 보존한다.
- HTTP EOF는 모델 응답의 의미상 완료와 다르다. 의미상 완료는 제한된 SSE 이벤트 타입 관측으로 따로 completed/failed/incomplete/unobserved를 기록한다.
- SSE 관측은 전달 경로를 버퍼링하지 않는 bounded observer로 구현한다. 본문을 보관하지 않고 알려진 종료 타입만 추출하며, 잘림·초과 크기·미지원 형식은 unobserved로 처리한다. 관측 실패 때문에 응답을 중단하지 않는다.
- 일반 WebSocket은 Hijack/Flush 및 양방향 전달을 보존한다. 핸들러 반환만으로 연결 완료라고 간주하지 않는다. 종료 원인을 확인할 수 없으면 unknown으로 기록한다.
- 취소와 upstream 장애가 경합하면 우선순위와 unknown 처리 규칙을 명시한다. 프로세스 강제 종료로 final 이벤트가 없으면 분석기가 미완결 요청으로 집계한다.

완료 기준: 200 후 강제 upstream 단절, 정상 EOF, 사용자 취소, 의미상 완료 미관측을 구분한다. 기존 SSE 즉시 전달과 일반 WebSocket 테스트가 통과한다.

### P3 — 보관·분석 환경

- Docker 로그에 제안 초기값 max-size=20m, max-file=5를 적용한다. 컨테이너 재생성이 필요하므로 P5에서 반영한다.
- 보관 상한은 기간 보장이 아니다. 최소 7일 비교를 위해 일별 집계 자료를 별도 로컬 runtime 경로에 저장하고 30일 후 정리한다. native 실행 시에도 동일한 용량 제한 또는 외부 회전 방법을 제공한다.
- 로그 출력은 제한된 큐를 사용하고 프록시 전달을 무기한 막지 않는다. 큐 포화 시 dropped_events와 집계 불완전 상태를 노출한다. 유실이 있는 보고서는 정상 판정 근거로 쓰지 않는다.
- 로컬 분석 명령을 제공한다. 예: `report --since 3h --timezone Asia/Seoul`, 또는 명시적 시작·종료 시각. 실제 명령 이름은 구현 시 CLI 구조에 맞춰 확정한다.
- stdout Docker 로그와 native JSONL 파일을 모두 입력으로 지원하며, 잘못된 라인·회전으로 누락된 시작 이벤트·구버전 로그를 별도 표시한다.
- 출력: 관측 범위/커버리지, 요청 수, 상태별 수, 경로별 4xx/5xx, 원인별 502, 지연 p50/p95/p99, 취소/중단/미완결, 전환 수, 데이터 유실 수.
- 지연은 경로·전송 종류별로 비교한다. 장시간 스트림 total 시간은 별도 표시한다. 소표본에는 표본 수와 불안정 경고를 붙이고 p99를 과해석하지 않는다.
- 시간 구간 중 활성 상태인 요청과 종료된 요청의 분모를 명시한다. 미완료 요청을 성공률 분모에서 몰래 제외하지 않는다.

완료 기준: 최근 3시간을 한 명령으로 분석하고 기록 부족과 실제 정상 상태를 구분한다. 재시작·로그 회전·용량 한도에서 동작을 검증한다.

### P4 — 회귀·정확성·관측 오버헤드 검증

합성 자격 증명과 로컬 upstream만 사용한다.

1. 정상 HTTP, 404/405, upstream 502, DNS/연결/TLS/timeout, 인증 실패의 이벤트 분류 검증.
2. 지연 헤더·지연 첫 본문·중간 단절·취소·SSE 종료 타입·큰 이벤트·분할 이벤트 검증.
3. Responses 426 전환 및 일반 WebSocket, quota 전환, 동시 요청의 상관관계와 최종 이벤트 중복 방지 검증.
4. 토큰·쿠키·ID·본문·쿼리·오류 메시지에 합성 비밀값을 심고 출력 전체에서 미노출 검증.
5. 기존 gateway/app/authbroker 테스트와 `go test ./...`, 지원되는 환경에서 `go test -race ./...` 수행.
6. 동일 머신과 부하에서 관측 off/on을 최소 3회 비교한다. 초기 예산은 로컬 HTTP p95 추가 지연 2ms 이하, 처리량 저하 5% 이하로 두고 측정 잡음을 함께 기록한다.
7. 긴 SSE·WebSocket과 느린 로그 소비자에서 메모리 증가가 요청 길이에 비례하지 않고 설정된 버퍼 상한에 머무는지 검증한다.

완료 기준: 측정값이 합성 시나리오와 일치하고 전달 동작 회귀가 없다. 환경상 실행하지 못한 검증은 통과로 표시하지 않는다.

### P5 — 운영 반영과 최적화 기준선

1. 기존 이미지 ID와 실행 명세를 확보하고 되돌릴 명령을 준비한다. 자격 증명은 복제하지 않는다.
2. 활성 스트림 상태를 확인하고 유예 종료를 적용해 기존 데이터 루트로 교체한다. 병렬 프록시가 같은 프로필을 사용하지 않게 한다.
3. 새 실행 버전, mount, loopback 포트, 로그 회전, health를 확인한다. 실제 요청에서 시작·헤더·최종 이벤트와 스트림 종료를 확인한다.
4. 관측이 불완전하거나 스트림 전달이 퇴행하면 이전 이미지와 실행 명세로 복구한다. 로그 스키마 및 분석기도 이전 버전 입력을 지원한다.
5. 24~72시간 기준선을 수집한다. 낮은 사용량이면 기간을 늘리고 경로별 표본 수를 보고한다.
6. 초기 조사 기준: 5분간 5xx 3건 이상, 경로별 최소 20건 중 5xx 5% 이상, 최소 30건에서 p95가 기준선 2배이면서 1초 이상 증가, client_cancel을 제외한 스트림 오류 반복. 이는 조사용 초기값이며 사용자 취소·의도된 426·소표본을 분리한다.
7. 실제 병목별로 한 번에 하나의 변경을 적용하고 같은 경로·전송·부하 조건에서 재측정한다. 오류율 개선 없이 지연만 좋아지거나 표본이 부족하면 최적화 성공으로 판정하지 않는다.

완료 기준: 첫 운영 보고서를 생성하고, 오류·지연·중단에 대한 근거와 비교 가능한 기준선이 확보된다. 예약 감시나 알림 자동화는 별도 요청 시 설정한다.

## 5. 실행 순서와 산출물

의존 순서: P0 → P1 → P2 → P3 → P4 → P5.

산출물은 이벤트 계약 문서, 계측 코드, 로컬 보고서 명령, 로그 보관 설정, 합성 검증 결과, 운영 반영/복구 절차, 첫 기준선 보고서다. 런타임 자료는 실제 확인한 호스트 상태 경로 아래에 두고 저장소에는 코드·계약·합성 예제만 둔다.

이 계획 작성에서는 제품 코드·운영 설정·컨테이너를 변경하지 않는다. 위 단계의 구현·운영 반영은 후속 작업이다.
